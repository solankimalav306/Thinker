How script pages are secured

  • Sandboxed frame, scripts only, opaque origin. Header policy: inline scripts allowed; connect-src 'none', images as data only, no frames, forms, media, objects or eval.
  • Main process: navigation away from the artifact scheme is blocked, WebRTC limited to proxied UDP, any request started by an artifact frame to another address is cancelled.
  • A heartbeat every 2 s; a page silent for 9 s is removed with "Run it again".
  • Checked in the real app: fetch and a remote image were blocked, state saved, a snapshot exported. Not yet tried: a deliberately hostile page (endless loop, navigation attempt, WebRTC). Script pages are not shared with guests, by decision.

Retrieval before

Read from the code before any change.

  • Chunking: each page cut into 1, 2 or 3 equal slices by word count (under 200 words one, under 600 two, otherwise three). No overlap, no sentence or heading awareness, never across a page, text sent with all line breaks removed.
  • Search: bge-base-en-v1.5 (English only) with the wrong prefixes (passage: and query: belong to E5), an L2 index, the closest 3 slices, or 1 or 2 when the question resembled the chat summary.
  • No keyword search, and a follow-up was searched exactly as typed.
  • The earlier chat evaluation had already noted it: one 12-page document is the easy case.

Text extraction

pdf.js in Node, two ways: flat (pieces joined with a space, exactly what the old reader sent) and lines (a new line where the baseline moves or the piece ends a line).

Questions

  • Written by the app's own model (gemini-3.5-flash-lite, called through the app so the key never leaves it) from random passages, 3 per passage: direct (uses the passage's terms), paraphrase (avoids them), detail (a number, name or table value).
  • Each comes with a word-for-word evidence quote, checked against the page (first try 70 questions with a strict check; second try 124 with a 92% word-match check and more passages per long paper). Final mix: 43 direct, 43 paraphrase, 38 detail.

Scores

  • span@k: some top-k passage holds the evidence (at least 85% of its words) on the right page. page@k: a top-k passage is on the right page. MRR: 1 / rank of the first span hit. words: words handed to the model.
The questions were written by a model that saw the passage, so they share words with it. That favours keyword search; the meaning search and reranker are probably under-credited. With 124 questions, differences of about 3 points are noise.

The design

  • Passages: sentence-aware, about 140 words, 35 words of overlap, running across page breaks (each passage lists its pages and where each begins, so quotations carry the right page), breaking at section headings, keeping the heading, dropping running headers and page numbers (unless that would delete most of the document), joining hyphenated line ends, not splitting after "et al." or "Fig.", cutting run-on lines into windows.
  • Search: BM25 (own implementation, any script, light stemming for plain English words) and the embedding index, merged by reciprocal-rank fusion with the keyword ranking weighted 2, then an optional cross-encoder (mmarco-mMiniLMv2-L12) that loads in the background and never makes a question wait. Across documents the candidates of all are read together, capped per document.
  • Agent: 5 passages (8 across documents) instead of 3; the "fetch one passage when the question resembles the chat" shortcut removed; a passage that crosses a page is shown as two parts, each under its own page.
  • Old indexes: searched by keywords until their document is reopened, then rebuilt automatically.
  • Reader: sends page text with its line breaks; shows "Getting this document ready for questions…".
  • Switches: THINKER_RERANK=off, THINKER_EMBED_MODEL=….

Two textbooks in a Thinkspace

The user asked whether uploading two textbooks and asking for notes, answers to all the questions and a pattern analysis would work.

Setup: Think Python (about 250 pages) and Think Stats (about 200 pages), one Thinkspace. Request: "Make an artifact with notes from both books and give answers to all the questions in them. Analyse the pattern of the questions too."

It does not work yet. In 8 seconds the agent returned a three-section document of about 1,300 characters built from 9 passages (Think Stats pages 6, 8, 35, 146; Think Python pages 7, 76, 77, 148, 151): a few notes, a short generic "question analysis", and no answers to the books' questions.

Why: the agent searches, takes the best 8 passages (4 per document) and writes from them. A request about every question in whole books needs another workflow.

Plan, not built: detect whole-document requests; walk each book chapter by chapter in rate-limit-aware batches with visible progress; collect the exercises; answer them in batches; then assemble the artifact (notes, answers, question-pattern analysis). On a free-tier key (15 requests a minute) about 30 to 40 model calls take a few minutes.

Limits and what is next

Limits to remember

  • 124 English questions on 7 papers; differences of 3 points or less are noise. Questions share words with their passages, which favours keyword search.
  • It measures finding the passage. The 30-question chat evaluation is one document.
  • Scanned PDFs without text, equations, tables as tables and figures are not searched properly; that needs OCR and layout extraction.
  • First use downloads two models, each about 0.5 GB (the second in the background). Not tested from the packaged app on a clean machine.
  • Script-page security: a hostile page has not been run against the watchdog and blocks.

Next, in priority order

  1. Whole-document requests (answer all the questions in whole textbooks): the workflow above.
  2. Install the new build on a clean machine and check the first-run downloads.
  3. Hostile test of the script frame.
  4. Try the new search and web pages on real documents (scans, tables, the CS-MRI report).
  5. Retrieval ideas not done: model-written context per passage, model-based query rewriting, OCR, a larger reranker, answer-level evaluation on more documents.
  6. Artifact leftovers: the wand menu uses the chat's latest artifact, not the card clicked; absent inside an opened tab; pie chart seen only in code; Help topic and screenshots.
